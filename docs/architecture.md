# Архитектура

Приложение организовано по направлению зависимостей:

```text
domain ← application ← presentation
          ↑                 ↑
          └ infrastructure ─┘
                 composition root: App
```

- `domain` хранит независимые правила: реквизиты подключения, `chatId`, ограничения текста.
- `application` владеет сценариями, нормализованным состоянием диалогов и портом `GreenApiPort`.
- `infrastructure` реализует порт через `fetch`, проверяет внешние JSON-ответы Zod-схемами и преобразует ошибки в безопасную модель.
- `presentation` связывает React-компоненты с reducer и жизненным циклом notification pump. `App` является composition root.

## Сессия и состояние

После валидации реквизитов создаётся сессия только в памяти вкладки. Повторное применение реквизитов отменяет старый pump и полностью сбрасывает диалоги, сообщения, unread и dedupe-набор; данные разных аккаунтов не смешиваются.

Reducer — единственный владелец нормализованного состояния: `conversationsById`, порядок диалогов, `messagesById`, массивы идентификаторов сообщений по `chatId`, активный чат и ограниченный набор ключей дедупликации. Компоненты получают производные данные, но не создают второй источник истины.

Новый чат создаётся асинхронно: domain нормализует только поддерживаемый российский/белорусский номер, infrastructure вызывает `CheckAccount`, а reducer получает уже подтверждённый положительный числовой MAX `chatId`. Результат привязан к `sessionId`, поэтому ответ старой сессии после переподключения отбрасывается. Формат `@c.us` не является identity приложения.

## Получение уведомлений

На сессию работает ровно один pump, не зависящий от активного чата:

```text
receive → classify → emit / ignore → delete → следующий receive
```

Валидное личное текстовое сообщение требует `senderData.chatType === "user"` и положительный числовой `chatId`; группы, каналы и боты игнорируются и подтверждаются. UNIX timestamp в секундах преобразуется адаптером в JS milliseconds. Остальные валидные receipts учитываются как ignored/malformed и подтверждаются. Пока `deleteNotification` не завершён, новый `receiveNotification` не начинается. Валидный `{result:false}` считается терминальным идемпотентным результатом, а транспортные/429/5xx ошибки повторяются с backoff. Фатальные auth/protocol ошибки останавливают pump. `AbortController` завершает старый цикл при смене сессии, offline или unmount.

## Ошибки и безопасность

Внешние данные считаются недоверенными. Адаптер проверяет форму ответа, не передаёт сырые body/URL в UI и возвращает `AppError` с безопасным текстом и признаком повторяемости. Токен и полный endpoint не входят в сообщения ошибок и логи приложения. При этом браузерный frontend принципиально не способен скрыть токен от DevTools или расширений — production-развёртывание требует контролируемого backend/proxy.

## Проверки

- Vitest: чистые доменные правила, reducer, классификация, backoff и pump.
- React Testing Library + jsdom: доступные формы, состояния интерфейса и интеграция provider.
- MSW: контрактные тесты HTTP-адаптера без реальной сети.
- Playwright: один реальный браузерный smoke с network routing для multi-chat, отправки, входящего сообщения, unread и порядка ack.

Решения подробнее зафиксированы в [ADR](./adr/).
